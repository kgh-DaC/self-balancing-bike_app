# 밸런싱 바이크 통신 프로토콜 명세 (코드 기반)

근거 파일 (모두 직접 읽음, 검증됨):
- `01.Arduino Code and Library/remote.ino` (파서, 버튼, 피드백)
- `01.Arduino Code and Library/self_balancing_bike.ino` (loop, 상수, 서보/모터 구동)
- `01.Arduino Code and Library/functions.ino` (Tuning, angle_calc, vertical 판정)

## 1. 링크 계층
| 항목 | 값 | 근거 |
|---|---|---|
| 보레이트 | 115200, 하드웨어 `Serial` (8N1은 Arduino 기본값) | `Serial.begin(115200)` |
| STX / ETX | 0x02 / 0x03 | remote.ino 1-2행 |
| 수신 버퍼 | AVR 기본 64바이트 (코드에 명시 없음, 일반 지식) | - |

확인하지 못한 것 (코드에 없음):
- 블루투스 모듈 종류(HC-05/06 클래식 SPP인지 HM-10류 BLE인지), 모듈의 보레이트 설정, 핀 연결(하드웨어 UART 0/1 가정). 사용자 확인 필요.
- 서보 방향(+가 물리적으로 좌/우 어느 쪽인지)은 코드만으로 알 수 없음. 실차 확인 필요.

## 2. 앱 → 바이크 프레임

### 2.1 조이스틱 (8바이트)
`STX, X百, X十, X一, Y百, Y十, Y一, ETX`
- X, Y는 `(값 + 200)`을 3자리 ASCII 숫자로 인코딩. 유효 값 -100~100 (즉 "100"~"300").
- 예: (0,0) = `02 32 30 30 32 30 30 03`, 문자열 "200200" + 프레임.
- 예: (50,50) = "250250", (-100,100) = "100300".
- 수신측은 `joyX-200`, `joyY-200` 후 범위(-100~100) 밖이면 프레임 전체를 무시(return). 숫자 문자 여부는 검증하지 않음.

### 2.2 버튼 (3바이트) `STX, c, ETX`
| c | 동작 |
|---|---|
| 'A' | buttonStatus bit0 ON |
| 'B' | bit0 OFF |
| 'C' | bit1 ON |
| 'D' | bit1 OFF |

buttonStatus는 세 파일 어디에서도 제어에 쓰이지 않는다(피드백 문자열 생성에만 사용되고 그 함수도 호출되지 않음). 즉 버튼은 현재 펌웨어에서 아무 동작도 하지 않는다.

### 2.3 파서 동작 (`readControlParameters`)
- `loop()`에서 10ms(`loop_time`)마다 한 번 호출. 호출당 최대 1프레임 처리.
- 첫 바이트를 읽어 STX가 아니면 그 1바이트만 버리고 다음 주기(10ms)에 재시도 (재동기화 느림).
- STX 이후 `Serial.available()`인 동안 읽음. 바이트가 127 초과면 break(오류). `i==2` 또는 `i==7`에서 ETX를 만나면 break.
- 디스패치는 `i==2`이면 버튼, `i==7`이면 조이스틱. 읽기 중 버퍼가 비어 루프가 끝나도 i 값만으로 디스패치하므로 프레임이 쪼개져 도착하면 ETX 검증 없이 처리되거나(i==7) 버려질 수 있음.
- 알려진 결함: i==7에서 cmd[7]이 ETX가 아니면 i가 8이 되어 `cmd[8]`(배열 범위 밖)에 쓰기 가능. 앱은 항상 정확한 8바이트 프레임만 보내야 함.
- 권고: 프레임을 한 번의 write로 전송, 50~100ms 주기. 10ms보다 빠르게 보내면 버퍼에 쌓여 지연이 생김.

## 3. 부호/값 처리와 계산 예 (핵심)

상수: `STEERING_MAX=350`, `SPEED_MAX=80`, `STEERING_CENTER=1500`. 변수 `steering_remote`, `speed_remote`는 `int`(소수 대입 시 0 방향으로 절삭). Arduino `map()`은 정수 연산(정수 나눗셈 절삭).

### 3.1 조향 X
```
if (|X| > 10):
    X>0: s = (-X*X + 0.1*X)/100.0      -> int로 절삭
    X<0: s = ( X*X + 0.1*X)/100.0
else s = 0
steering_remote = -map(s, -100, 100, -350, 350)
```
- 데드존: |X| <= 10 이면 0.
- 비선형(제곱) 곡선. 부호는 두 번 뒤집힘(곡선에서 X>0이면 음수, map 후 앞의 `-`로 다시 양수) -> 결과적으로 X와 같은 부호.
- 서보 명령: `steering_value`가 `1500 + steering_remote`를 향해 10ms당 5(ST_LIMIT)씩 램프. `steering_servo.write(steering_value)` (ServoTimer2, 값 544 이상은 마이크로초 펄스로 해석 -> 약 1150~1850us 범위).

계산 예:
| X | 곡선 s (절삭 후) | map 결과 | steering_remote | 서보 목표(us) |
|---|---|---|---|---|
| +50 | (-2500+5)/100 = -24.95 -> -24 | (-24+100)*700/200-350 = 266-350 = -84 | **+84** | 1584 |
| -50 | (2500-5)/100 = 24.95 -> 24 | 124*700/200-350 = 434-350 = 84 | **-84** | 1416 |
| +100 | -99.9 -> -99 | 1*700/200-350 = 3-350 = -347 | **+347** | 1847 |
| -100 | 99.9 -> 99 | 199*700/200-350 = 696-350 = 346 | **-346** | 1154 |
| +11 | (-121+1.1)/100 = -1.199 -> -1 | 99*700/200-350 = 346-350 = -4 | **+4** | 1504 |
| +10 / 0 | 0 | 0 | 0 | 1500 |

결론: X 양수 -> steering_remote 양수 -> 서보 펄스 > 1500us. 물리적 좌/우는 서보 장착에 따라 다르므로 실차 확인 필요(코드로 확인 불가).

### 3.2 속도 Y
```
if (|Y| > 10): speed_remote = map(Y, 100, -100, SPEED_MAX, -SPEED_MAX)
else speed_remote = 0
```
`map(x, 100, -100, 80, -80)`은 입력 범위와 출력 범위가 모두 뒤집혀 있어 상쇄된다. 결과는 **부호 반전이 없는 선형 스케일 `speed_remote = Y*0.8`** (절삭).
- Y=+50: (50-100)*(-80-80)/(-100-100)+80 = (-50)(-160)/(-200)+80 = -40+80 = **+40**
- Y=-50: (-150)(-160)/(-200)+80 = -120+80 = **-40**
- Y=+100 -> +80, Y=-100 -> -80, Y=+11 -> 8 (8.8 절삭), |Y|<=10 -> 0.
- 구동: `steering_servo2.write(1500 + speed_remote*7)` (서보2, 핀 10). Y=+50 -> 1500+280 = **1780us**; 범위 1500±560 = 940~2060us. 이 경로에는 램프(속도 제한)가 없어 즉시 반영됨. (`speed_value`/`Motor2_control` 경로는 주석 처리됨.)
- 따라서 "화면 위쪽(전진)이 -가 되도록 펌웨어가 반전"이라는 기존 스킬 설명은 틀림. Y 양수 = 서보2 펄스 증가. 전진/후진 물리 방향은 실차 확인 필요.

### 3.3 (X=+50, Y=+50) 요약
프레임 "250250" -> `steering_remote = +84`, `speed_remote = +40` -> 조향 서보 목표 1584us(10ms당 5씩 도달), 서보2 1780us.

## 4. 바이크 → 앱
1. `sendControlParameters()`는 정의만 있고 어디서도 호출되지 않음(세 파일 grep 수준 확인). 형식: `STX + 6자리 버튼상태 + 0x01 + "0" + 0x04 + "0" + 0x05 + "0" + ETX`. 버튼상태 문자열은 MSB부터 6비트(bit5..bit0), bit0이 마지막 문자.
2. 실제로 송신되는 것은 **ASCII 디버그 텍스트 (println, 줄끝 \r\n)**:
   - 부팅 시: "Read calibration data!" 또는 "Has no calibration data!", "Read PID data!" 또는 "Has no PID data!", 약 3초 뒤 + 자이로 보정 후 "GyX offset: <값>".
   - 2초마다, `!calibrated && !calibrating`이면 "first you need to calibrate the balancing point...".
   - Tuning 모드 시: "calibrating on/off", "AcY: .. AcZ: ..", "K1: .. K2: .. K3: .. K4: ..".
   앱은 수신 텍스트를 로그로 보여주면 상태(캘리브레이션 여부) 진단에 유용. STX 프레임이 아니므로 STX 파서와 혼동하지 말 것.

## 5. 디버그/튜닝 모드
- `self_balancing_bike.ino` loop에서 현재 `//Tuning();` 주석, `readControlParameters();` 활성. 둘은 같은 Serial을 읽으므로 동시 사용 불가(펌웨어 재업로드로 전환).
- `Tuning()`: 2바이트 `[param][+|-]`. 수신 후 `delay(2)`, 두 번째 바이트 없으면 무시, 이후 `Serial.flush()`.
  - 'p': K1 +-1.0, 'i': K2 +-0.5, 's': K3 +-0.2, 'a': K4 +-0.05. 매 명령마다 EEPROM(주소 50, ID 55)에 저장(마모 주의) 후 K 값 출력.
  - 'c'+: calibrating=true, 'c-': (calibrating일 때만) `offsets.AcZ = AcZ+16384`, `offsets.AcY = AcY`, ID=35로 EEPROM(주소 0) 저장, calibrated=true.
- 기본 이득: K1=24, K2=-20, K3=-9, K4=0 (EEPROM에 PID 데이터가 있어도 현재 코드는 부팅 시 K 값에 적용하지 않고 `PIDHas` 플래그만 설정함: setup에서 MyPid를 K1~K4에 복사하는 코드 없음).

## 6. 안전 관련 사실 (별도 정리)
1. **구동 조건**: `vertical && calibrated && !calibrating`일 때만 브레이크 해제(pin 8 HIGH), 균형 모터 및 서보 구동. 아니면 브레이크 LOW, 두 서보 중립(1500), 모터 0, 원격 입력은 반영되지 않음.
2. **vertical 판정**: `|robot_angle| > 10deg`이면 false, `|robot_angle| < 0.3deg`이면 true (히스테리시스). 즉 한 번 쓰러지면 0.3도 이내로 세워야 재가동. 기동 직후 약 3초 대기 + 자이로 오프셋 1024샘플(약 3초+) 동안 기체를 정지시켜야 함.
3. **캘리브레이션 필수**: EEPROM ID 35 없으면 calibrated=false로 절대 구동 안 함. 캘리브레이션은 Tuning 모드의 `c+`/`c-`로만 가능하며, 현재 빌드(원격 모드)에서는 웹 앱으로 불가. 수평 정지·직립 상태에서 수행(AcZ에 16384 가정).
4. **통신 두절 failsafe 없음**: 타임아웃/워치독이 없다. 앱이 끊기거나 멈추면 마지막 `steering_remote`, `speed_remote` 값이 유지되며 vertical 상태에서는 계속 서보에 적용됨(서보2는 램프 없음). 따라서 앱이 연결 직후, 해제/오류/탭 숨김/입력 해제 시 반드시 "200200" 중립 프레임을 보내야 하고, 가능하면 주기 전송을 끊지 말고 중립으로 전환. 링크가 완전히 끊긴 경우는 앱이 보낼 수 없으므로 펌웨어 측 보완이 필요(제안 사항).
5. **입력 범위**: -100~100 밖은 펌웨어가 무시(이전 값 유지)하므로 앱은 클램프 후 인코딩. 무시된 프레임은 "중립 요청"이 전달되지 않는 것과 같음에 유의.
6. **재개 시 이전 값**: 비-vertical 중에도 steering_remote/speed_remote 변수는 유지되어, 다시 vertical이 되면 이전 입력이 즉시 적용될 수 있음. 앱은 상태 복귀 시 중립을 먼저 보낼 것.
7. **배터리**: 전압 8~9.5V 구간에서 부저 경고(`bat_divider=58` 보정 필요). 앱에서 읽을 수 있는 경로 없음.
8. 파서 결함(2.3의 배열 범위 밖 쓰기)로 인해 잘못된 길이 프레임을 보내지 말 것.

## 7. 스킬 수정 사항 (코드가 정답)
1. **Y 부호 설명이 틀림**: 스킬은 "화면 위쪽(전진)이 -가 되도록 펌웨어가 반전"이라 했으나, `map(joyY,100,-100,80,-80)`은 이중 반전으로 상쇄되어 `speed_remote = 0.8*Y` (부호 유지). Y=+50 -> +40. 수정 필요.
2. **X 부호 설명 보완**: "펌웨어가 반전 처리"는 맞지만 곡선의 음수화와 앞의 `-`가 상쇄되어 최종적으로 X와 같은 부호(X=+50 -> +84). 또한 제곱 곡선과 절삭 때문에 +100은 +347, -100은 -346으로 약간 비대칭. 데드존 ±10 포함 경계: |X|<=10이면 0.
3. **"바이크 → 앱" 항목 보완**: 구조 프레임은 안 보내지만, 부팅 메시지와 2초 주기 "first you need to calibrate..." 등 ASCII 텍스트가 같은 UART로 송신됨.
4. **구동 출력 설명 추가**: 속도는 서보2(핀 10)를 `1500+speed_remote*7`로 구동(Motor2는 주석 처리), 조향은 A3 서보를 10ms당 5 램프. 속도 쪽은 램프 없음.
5. **버튼 A~D는 현재 펌웨어에서 아무 효과 없음**을 명시.
6. **통신 두절 failsafe 부재**와 파서 i==7 ETX 미검증/배열 초과 결함 명시.
7. **vertical 임계값 구체화**: 해제 >10deg, 재진입 <0.3deg.
8. 스킬의 "모든 바이트는 127 이하" 및 프레임 형식, 보레이트, 캘리브레이션 설명은 코드와 일치(검증됨). 블루투스 모듈 종류와 BLE/SPP 연결 방식, UUID 부분은 코드로 검증 불가(미검증, 일반 지식).
9. Tuning 모드 PID: 부팅 시 EEPROM PID를 K에 로드하는 코드 없음을 스킬에 참고로 추가(튜닝 패널 사용 시 재부팅하면 기본값으로 돌아갈 수 있음).
